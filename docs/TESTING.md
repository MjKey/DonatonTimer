# Тестирование DonatonTimer

## Быстрый запуск

Нужен Flutter stable с Dart, совместимым с `environment.sdk` в `pubspec.yaml`.
Все команды выполняются из корня репозитория. Команды тестирования работают
на Windows и в Linux CI; запуск Windows-приложения для них не требуется.

```powershell
flutter pub get
flutter test --tags unit
flutter test --tags widget
flutter test
```

Первая команда устанавливает зависимости; при первом запуске нужен доступ к сети.
`flutter test --tags unit` запускает только быстрые unit-тесты.
`flutter test --tags widget` запускает widget-тесты интерфейса.
`flutter test` запускает весь набор, включая компонентные тесты адаптера с локальным
WebSocket-сервером. Компонентная группа занимает около 45 секунд: она проверяет
настоящие интервалы ping, переподключения и обновления авторизации.

При успехе команда завершается с кодом `0` и сообщением `All tests passed!`.
Код завершения, отличный от `0`, означает неуспешную проверку; сообщение ошибки
показывает название сценария и причину.

## Отдельные проверки

| Задача | Команда |
| --- | --- |
| Только unit-тесты | `flutter test --tags unit` |
| Только widget-тесты | `flutter test --tags widget` |
| Только компонентные тесты | `flutter test --tags component` |
| Один unit-файл | `flutter test test/services/donation_alerts_adapter_unit_test.dart` |
| Весь адаптер с локальным сервером | `flutter test test/services/donation_alerts_adapter_test.dart` |
| Сценарий heartbeat | `flutter test test/services/donation_alerts_adapter_test.dart --plain-name "sends Centrifugo ping and keeps the subscription active"` |
| Тесты провайдера тем | `flutter test test/providers/theme_provider_test.dart` |
| Тесты стилей интерфейса (widget) | `flutter test test/screens/app_ui_style_test.dart` |
| Подробный вывод | `flutter test --reporter expanded` |
| Покрытие | `flutter test --coverage` |
| Статический анализ | `flutter analyze` |

Покрытие сохраняется в `coverage/lcov.info`; каталог исключён из Git.
Покрытие помогает находить непроверенные ветки, но не заменяет проверки поведения.
Если полный анализатор сообщает о существующих замечаниях в других файлах,
отдельно проверьте затронутые пути, например:

```powershell
flutter analyze lib/services/donation_alerts_adapter.dart test/services
```

Существующие замечания указывайте отдельно от ошибок, добавленных изменением.

## Архитектура тестов

Тесты располагаются отдельно от приложения и повторяют структуру `lib/`.
Реализации для тестов не должны попадать в `lib/` или запускаться из `main.dart`.

```text
lib/
  models/
  providers/
  services/
    donation_alerts_adapter.dart
test/
  providers/
    theme_provider_test.dart
  screens/
    app_ui_style_test.dart
  services/
    donation_alerts_adapter_unit_test.dart
    donation_alerts_adapter_test.dart
```

Для новых классов создавайте соответствующие файлы в `test/models/`,
`test/providers/` или `test/services/`. Общие тестовые реализации выносите в
`test/support/`, когда они действительно используются несколькими наборами.

| Уровень | Что проверять | Зависимости |
| --- | --- | --- |
| Unit (`unit`) | Чистые преобразования, расчёты, валидацию, поведение одного класса | Подставные реализации внешних зависимостей; без сокетов, диска и реального ожидания |
| Widget (`widget`) | Отрисовку и взаимодействие с экранами/диалогами через `testWidgets` | Подставные сервисы, провайдеры и SharedPreferences в памяти |
| Компонентные проверки сервисов (`component`) | Обмен командами адаптера, состояния, потоки событий, таймеры и переподключение | HTTP-заглушка и локальный WebSocket-сервер на `127.0.0.1` со случайным портом |
| Полное приложение | Сценарии запуска, платформенные плагины и реальный UI Windows | Запуск собранного приложения на Windows с тестовым сервером |

## Проверка стилей интерфейса

Тесты `test/providers/theme_provider_test.dart` проверяют сохранение выбора,
совместимость с настройками существующих установок и независимость цветовой темы.
Widget-тесты `test/screens/app_ui_style_test.dart` проверяют переключение через
настройки без сброса таймера и данных, светлую/тёмную темы, диалоги сброса и панели
редактора с растягиваемым содержимым.

Проверки используют подставные SharedPreferences и хранилище в памяти. Они не
читают пользовательские настройки и не подключаются к сервисам донатов.

Ручная проверка на Windows: откройте «Настройки → Внешний вид», переключите стили
«Ретро (версия 3)» и «Классический (версия 2)» при работающем таймере, проверьте
светлую/тёмную темы, настройки, диалоги и редактор OBS. Перезапустите приложение
и убедитесь, что выбранное оформление сохранилось.

## Правила новых тестов

1. Название сценария описывает наблюдаемое поведение. Названия и комментарии
   в Dart-файлах пишутся на английском.
2. Проверяйте результат, ошибку или переход состояния через публичный API.
   Порядок транспортных команд проверяйте там, где он является частью протокола.
3. При исправлении бага добавляйте сценарий, воспроизводящий его причину:
   например, ответ ping с одним `id` или донат без `alert_type`.
4. Используйте только фиктивные токены и тестовые данные. Автоматические тесты
   не читают `%APPDATA%`, пользовательские настройки или присланный HTML
   и не подключаются к DonationAlerts.
5. Создавайте изолированное состояние в `setUp`. Закрывайте адаптеры, подписки,
   серверы и клиенты в `tearDown` или `addTearDown`, в том числе после неудачной
   проверки.
6. Для асинхронных операций ожидайте событие, поток или `Completer` и задавайте
   ограничение времени. Реальное ожидание оставляйте в компонентном наборе,
   когда оно непосредственно проверяет поведение таймера. В unit-тестах
   используйте управляемое время при необходимости тестировать таймеры.
7. После изменения сначала запускайте затронутый файл, затем полный
   `flutter test` перед PR. Исправления документации и комментариев
   не требуют повторного прогона тестов.

## CI и релиз

Workflow `.github/workflows/test.yml` запускает `flutter test --reporter expanded`
на Linux при push в ветку, для pull request и вручную. У workflow только право
чтения репозитория; секреты и токены сервисов не нужны.

В `.github/workflows/build.yml` тот же набор запускается на Windows перед сборкой
релиза. Ошибка тестов останавливает шаги сборки и упаковки установщика.

Workflow-файлы начинают действовать после отправки изменений в GitHub.
Чтобы запретить слияние PR с падающими тестами, владелец репозитория должен
отдельно добавить проверку `Unit and component tests` в обязательные проверки
правила защиты ветки; один workflow не включает такую защиту автоматически.

Проверка настоящего DonationAlerts остаётся отдельным ручным сценарием:
она требует рабочего токена и внешнего сервиса и не входит в автоматический CI.
